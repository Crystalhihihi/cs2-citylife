# Spike 报告：CLI 链路实测（M0 ③）

> 日期：2026-08-19 ｜ 对象：Kimi Code CLI（`~/.kimi-code/bin/kimi`）headless one-shot ｜ 样本：5 发小样（脚本 smoke test，50 发全量待跑）
> 结论先行：**链路可用**——输出能稳定拿到纯 JSON、延迟 9-15s 在异步节拍预算内、无 429；**token/usage 统计不暴露在输出里**，网关的 token 记账需另想办法。

## 1. 实测数据（5 发，同固定前缀 + 尾部编号）

| 指标 | 结果 |
|---|---|
| 成功率 | 5/5，无 429、无超时 |
| 延迟 | avg 11.2s，min 9s，max 15s（含进程起停 + 模型时间） |
| JSON 纯净度 | text 模式输出带 `• ` 前缀（`kimi -p` transcript 风格，官方文档已载），剥掉前缀后内容即纯 JSON |
| stream-json | `{"role":"assistant","content":"…"}` 单行 JSONL，content 内为纯 JSON；另有 `role:"meta"` 行（session 恢复提示），解析需按 role 过滤 |
| usage/token | **stream-json 样本中未发现 usage 字段** |

## 2. 对网关设计（§4 M3）的影响

1. **解析路线定为 stream-json**：按 `role=="assistant"` 取 `content`，比 text 模式剥前缀稳；`meta` 行直接丢弃。
2. **延迟预算成立**：10-15s/发 × 小并发 2-3，对"平台池 1-2 游戏分钟一炉、闲聊池 3-5 分钟一炉"的节拍绰绰有余；全 one-shot + 异步后台线程的架构决策不受影响。
3. **token 统计降级方案**（usage 不暴露的现实）：网关先做**字符级估算记账**（prompt/response 字符数按经验系数折算 token），并在统计日志里留 usage 字段位——若 `kimi web` 本地 REST 服务暴露 usage（M3 传输层对比时一并验证），再切换精确记账。缓存命中也因此**无法从 usage 直接验证**，只能间接观测（同前缀重复调用的延迟趋势；本次 5 发样本太少，9-15s 方差内看不出）。
4. **缓存纪律不变**：固定前缀+动态尾部照写，它是"有则受益、无则无害"的正交纪律。
