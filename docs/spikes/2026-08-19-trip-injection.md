# Spike 报告：TripNeeded 注入压测（M0 ④）

> 日期：2026-08-19 ｜ 环境：CS2 1.6.x（Steam）+ `--developerMode` ｜ 测试城：新开档，~3000 市民，口袋公园×1，雨天
> 结论先行：**priority 抢占成立；3000 人级城市 947 人秒注无卡顿；"翘班"效果持续到休闲行程自然走完，工作调度中途抢不回去。**

## 1. 目的

验证设计文档 §9 M0 spike ④ 的两个问题：

1. 高 priority 的注入行程能否抢占市民的上班调度（"翘班"，烟花节事件链的关键）
2. 大规模同时注入对寻路性能的影响（疯狂档可行性的前提）

## 2. 方法

注入写法依据 Time2Work `SocialTripSystem.cs:309-379`（社区验证模式，见调研纪要）：

- `DynamicBuffer<TripNeeded>` 挂**市民本人**，主线程 `EntityManager.GetBuffer` 直写
- 只填 `m_TargetAgent`（目标建筑实体）/ `m_Purpose=Leisure` / `m_Priority`，`m_Data/m_Resource` 留默认
- 配套三件套：设 `Target`、写 `TravelPurpose{Leisure}`、移除 `Leisure/PathInformation/PathElement`
- 分批 50 人/帧错峰；同目标+同目的去重
- 目标建筑：带 `AttractivenessProvider` 组件的建筑（公园等；实测标志性建筑/墓地**不带**此组件）
- 触发：Ctrl+K（100 人/128/只抓正在上班）与 Ctrl+L（2000 人/255/全体市民）

代码：`src/CimLife/GameBridge/InjectionSpikeSystem.cs`（spike 性质，正式版重写为带上限的原语执行器）。

## 3. 实测数据

**第一波（128，上班市民定向）**：

```
开波前：GoingToWork≈100 Working≈90 Leisure≈5
波后：  Leisure 251，持续 >1 分钟未回落；GoingToWork/Working 一度归 0
```

**大波（255，全体市民）**：

```
947 人注入，全程 <2 秒（50/帧），无错误日志，帧率无体感变化
普查：Leisure 2901 / 总数 2908；2.5 分钟后仍 ~2900
GoingToWork 从 0 缓慢爬回 1（恢复观察中）
第二波 +0：去重生效（2900 人已全覆盖）
```

## 4. 结论

1. **抢占成立**：激活的 Leisure 行程**不被工作调度中途抢回**——"翘班"效果持续到行程自然完成（本测试观测窗口 >1 分钟未回落，对应 1-2 游戏小时量级）。128 与 255 在"是否站住"上无差异（差异预计体现在队列排序，未单独观测）。
2. **注入性能**：3000 人级城市秒注 947 无卡顿、无洪峰（分批 50/帧 有效）。**50 万人口级未验证**，需要大城存档复测。
3. **目标组件要求**：`AttractivenessProvider` 是可靠的目标筛选器；非休闲目标的 Leisure 注入行为未验证（Time2Work 也只打公园，推测会被游戏秒取消）。

## 5. 对设计的影响

- **事件包规模上限要按"完成前不回班"理解**：被注入市民在行程完成前不参与工作调度，疯狂档"全城翘班"是字面意义的真全城——警告文案有据可依。
- **恢复逻辑 = 行程自然完成 + 排班回拉**，无需主动"解散"原语；恢复时长 ≈ 休闲行程时长（1-2 游戏小时），事件包冷却应大于此。
- **画像过滤可行**：Worker/TravelPurpose 组合过滤已验证（配合 spike ① 的 CitizenFlags 年龄位，五旋钮中"画像"一钮技术通路全通）。
- 感知率副产品：本次测试在**雨天**进行，注入行程照常执行——天气不影响已注入行程（Time2Work 的天气因子只影响自然休闲概率）。

## 6. 未关闭 / 后续

- 50 万人口级压测（需要大城存档）
- 恢复曲线已确认：大波后 6 分钟 Leisure 2901→1980、GoingToWork 0→54、"其他"（回家等）7→805——"行程完成+排班回拉"如预期工作，完全恢复量级约 2-3 游戏小时
- **肉眼确认（同日实机）**：注入人群在公园周边道路造成真实交通拥堵——"聚集→拥堵"涌现链视觉成立，感知率最原始验证通过
